# ADR 0010 · 数据层从 localStorage 搬到 SQLite

- 日期：2026-08-30（产品线开线八项裁决之一）
- 状态：生效
- 相关代码：`src/store/store.ts`、`server/db/`

## 背景

比赛版的演示数据全在浏览器 localStorage 里。产品线要求多患者 + 多康复师，
浏览器存储无法支撑：数据不跨设备、不留存、无法做权限。

改造前做过一次影响面盘点（见 [接后端时改哪里](../接后端时改哪里.md)），
结论是：**除了 `src/store/store.ts`，没有任何页面直接碰 localStorage**。
改造面被收拢在一个文件里。

## 备选

1. **保持 localStorage**：不满足产品线需求。
2. **换成 IndexedDB**：仍是浏览器内，不解决跨设备与权限。
3. **服务端 SQLite**：需要引入后端，但一步到位。

## 裁决

**服务端 SQLite**（better-sqlite3），分六阶段实施：
P1 数据层 → P2 鉴权 → P3 业务接口 → P4 患者上下文 → P5 知识库 → P6 审核后台。

## 后果

- 落地规模：**28 张表 / 21 个索引 / 3 支迁移 / 49 个路由处理器**。
- **`store.ts` 对外的 14 个函数签名一个都没改，16 个消费方零改动** ——
  这正是改造前把边界收拢到一个文件的回报。
- 启动即建连跑迁移，让"表缺失"这类问题在启动时暴露，而不是等第一个请求。
- 空库自动灌种：部署环境没人手动跑 `pnpm seed`，不灌的话连登录账号都没有。
  只在 `users` 表为空时执行，已有数据的库绝不重灌。
- 引出两条新约束：写操作要保持同步手感（[0012](0012-写操作乐观更新.md)）、
  跨端实时要重做（[0011](0011-实时推送不用-EventSource.md)）。
