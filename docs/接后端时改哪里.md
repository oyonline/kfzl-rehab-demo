# 接后端与数据库时，改哪里

写于 2026-08-30。此时项目**没有**后端数据层，演示数据全在浏览器 localStorage 里。

这份文档回答一个问题：**将来要把数据搬到数据库，具体动哪些文件、哪些函数、
按什么顺序、有哪些已知的坑。** 不含代码，也不代表已决定要做。

> 当前结论：比赛前不做。演示不需要跨设备、不需要留存，
> 而改动数据层会给现场多一个故障点。详见文末「为什么现在不做」。

---

## 一、好消息：改造面已经被收拢到一个文件

全仓搜过：**除了 `src/store/store.ts`，没有任何页面直接碰 `localStorage`。**
（2026-08-30 实测：其余文件里出现的 localStorage 全是注释，无一处调用。）

```
src/store/store.ts               ← 唯一的演示数据边界，313 行 —— 要搬的就是它
src/auth/auth.ts                 ← 登录态，sessionStorage，刻意不搬，见坑 2
src/components/ReminderBanner.tsx ← 提醒浮层「已关闭」标记，sessionStorage
```

后两个都是**本地临时状态**，不是业务数据：换机器、换浏览器丢了也无所谓。
搬数据层时**不要顺手把它们一起搬走**，尤其是登录态（见第五节坑 2）。

页面拿数据只有一条路：`useDemoState()`；写数据只有下面这些函数。
**换成后端，改这一个文件；所有页面一行都不用动。**

这不是运气，是当初就按这个边界写的。请后来者继续守住 ——
一旦哪个页面直接读写存储，这份文档就作废了。

## 二、写操作清单（要变成 API 的就是这些）

| store 函数 | 谁在调 | 建议的接口 |
|---|---|---|
| `setCheckIn(taskId, status, note?, date?)` | 今日安排的打卡/撤销、视频页完成打卡、困难反馈 | `PUT /api/checkins` |
| `addVital(systolic, diastolic, by?)` | 家属端健康数据录入 | `POST /api/vitals` |
| `addUpload(taskId, filename, sizeLabel, videoId)` | 视频页模拟上传 | `POST /api/uploads` |
| `addMessage(msg)` | 咨询对话（家属提问、AI/预设回答） | `POST /api/messages` |
| `addGuidance(text, therapistName, aboutTaskId?, aboutDate?)` | 康复师端写指导、血压预警下回写 | `POST /api/guidances` |
| `markGuidanceRead(id)` / `markAllGuidanceRead()` | 家属端进今日页自动标已读 | `PATCH /api/guidances/:id` |
| `createEscalation(input)` | 对话转人工、任务困难反馈 | `POST /api/escalations` |
| `answerEscalation(id, answer, therapistName)` | 康复师端待处理里回复 | `PATCH /api/escalations/:id` |
| `resetDemo()` | 演示前重置 | `POST /api/demo/reset` |

读操作只有 `useDemoState()` 一个入口，对应 `GET /api/state`
（或按资源拆成几个 GET，看是否要做增量）。

派生函数 `todayCheckIns` / `effectiveStatus` / `pendingEscalations` /
`todayVitals` / `hasAbnormalVital` 是**纯计算**，不碰存储，原样保留即可。

## 四、改造顺序

1. **先起接口，不动前端。** 在 `server/index.ts` 里加上面那些路由，
   用 SQLite（better-sqlite3，单文件、无独立进程，参赛人电脑不用多装服务）。
   此时前端仍走 localStorage，两套并行，可随时回退。
2. **再换 store.ts 内部实现。** 把 `read()` / `write()` 换成 fetch，
   对外的 14 个函数签名**一个都不要改**。页面零改动。
3. **最后处理实时性**（见下一节）。

---

## 五、四个已知的坑

**1. 跨端实时刷新会失效。**
现在两端联动靠的是浏览器 `storage` 事件：同源另一个标签页写了 localStorage，
本端立刻收到。换成后端后这个事件不再触发，**康复师端不会自动刷新** ——
而「家属端打卡 → 康复师端立刻看到」是整个演示的主线。
需要补：轮询（最省，2–3 秒一次够用）或 SSE（`server/index.ts` 已经有
SSE 的写法可参照，见 `/api/chat`）。**这一步不做，主线就断了。**

**2. 登录态不要一起搬。**
`auth.ts` 用 sessionStorage 是刻意的：按标签页隔离，两端并排演示才不会
互相顶掉会话。搬到服务端 session/cookie 会同源共享，**两个角色无法同时在线**。
这条在 v0.2 §5.5 里是硬约束，实测踩过。

**3. 版本不一致会静默丢数据。**
现在 `SCHEMA_VERSION` 不一致的两个标签页会互相用初始状态覆盖对方，
表现是「刚录入的记录转眼就没了」且不报错（2026-08-29 实测踩到，
已在 storage 事件里加了版本守卫）。换后端后这个具体问题消失，
但**同类问题会以「前端旧版本调新接口」的形式回来**，接口要带版本号。

**4. 演示前重置的路径要保留。**
现在清 localStorage 就重置了。换后端后要有一个明确的重置入口，
否则每次彩排的数据会累积到正式演示那天的图表上。

---

## 六、为什么现在不做（2026-08-30 的判断）

- **演示用不上。** 两端是同一台电脑的两个窗口，localStorage 完全够；
  不需要跨设备、不需要跨天留存。
- **改造面已经收拢好了。** 现在加不会让以后更容易 ——
  以后要改的本来就只有 `store.ts` 一个文件。
- **给现场多一个故障点。** 现在两端联动是浏览器内存级的，不可能卡；
  走了数据库，打卡 → 写库 → 另一端读到，任何一环卡住就是演示事故。
- **时间。** 8/31 确认门、9/10 封版。在确认门前一天动数据层，
  是拿最稳的那条链路去换一个演示上用不到的东西。

**什么时候该做**：要跨设备演示（家属用平板、康复师用电脑）、
要留存真实数据、或者确定往真实产品走。**前两条现在都不成立。**

真到了做真实产品那一步，架构会重新来过（多租户、鉴权、隐私合规、
真实病历审计），那时候这份文档也只对「怎么拆掉 localStorage」这一段有用。
