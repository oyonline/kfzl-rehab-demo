## 1. 架构总览

```
浏览器 (React 19 / Vite)
   │  Bearer token (sessionStorage)
   ▼
Express 单进程  server/
   ├── auth/      JWT 签发校验、密码 scrypt、行级权限
   ├── db/        better-sqlite3 + 迁移 + 种子
   ├── routes/    业务接口 ~22 个
   ├── events/    SSE 推送（替代 storage 事件）
   ├── kb/        语料管道 + FTS5 检索 + 出处
   └── llm/       现有 /api/chat 改造为「先检索后生成」
   ▼
data/app.db   (SQLite 单文件，不进仓)
```

**为什么仍是 SQLite**：单文件、无独立进程、参赛人与部署机都不用装服务，保住「断网可演」这条既有硬约束。当前数据量（7 患者 × 数月记录 + 57 篇语料）离 SQLite 的能力上限差好几个数量级。真到多机构多租户再迁 Postgres，届时 SQL 层改动可控。

## 3. 鉴权设计

### 3.1 关键约束：必须用 Bearer token，不能用 Cookie

v0.2 §5.5 是实测踩过的硬约束：登录态同源共享 → 两端并排演示互相顶掉会话。**Cookie 天然同源共享，一旦用 Cookie 这条约束就当场违反。**

解法：**JWT 存 `sessionStorage`，请求走 `Authorization: Bearer` 头。**
- 是真实鉴权：服务端签发、校验、可过期、可吊销；
- 保留标签页隔离：`sessionStorage` 按标签页隔离，左右两窗可分别登家属与康复师。

即「搬到服务端」与「不互顶」两个要求可以同时满足，代价只是不能用 Cookie。**这一条请你确认——它是本方案里唯一一处对你决策 4 的技术性收窄。**

### 3.2 实现

- 密码：`node:crypto` 的 `scrypt` + 每用户随机 salt，零新依赖，不引 bcrypt。
- 令牌：HS256 JWT，`jose` 库（约 100KB，无传递依赖）；access token 8 小时，够一天演示/工作。
- 中间件：`requireAuth` 解析 token → `requirePatientAccess(patientId)` 查 `patient_members` → 无权返回 403。
- 首次启动种子账号沿用 `chen` / `xiaoting`，密码 `123456` 但**存的是 hash**；生产部署强制改密。

### 3.3 前端改动

`src/auth/auth.ts` 的三个导出函数签名不变（`signIn` 改为 async），内部换成调 `/api/auth/login` 并把 token 存进同一个 `sessionStorage` key。`RequireAuth.tsx`、`LoginPage.tsx` 与两个 Shell 共 4 个文件受影响。

### 4.3 检索实现

**分词**：SQLite FTS5 对中文不分词，`trigram` 精度一般。采用 **bigram 方案**——入库时把 chunk 正文切成二字滑窗串（「脑卒中康复」→「脑卒 卒中 中康 康复」）存进 `kb_chunks.bigram`，用默认 `unicode61` 建 FTS5 索引；查询时同样 bigram 化。中文全文检索的成熟做法，BM25 由 FTS5 提供，**零额外依赖、零模型、断网可用**。

**切片**：按 docx 段落与小标题聚合，目标 300–500 字、重叠 80 字。57 篇 / 8 万字约产出 300–400 个 chunk——规模极小，检索延迟在毫秒级。

**去重**：近重复文档按标题相似度 + 内容指纹聚成 `dup_group`，同组在 topK 内只保留最高分 1 条，避免「腿无力」4 篇挤满结果。

**为什么不上向量**：8 万字语料、约 350 个切片，BM25 的召回已经够；上向量要么引本地模型（包体积、CPU）要么依赖云端 embedding（违反断网约束）。架构上 retriever 做成接口，将来语料上量再加向量或混合排序，不用推倒。

### 4.4 `/api/chat` 改造

```
家属提问
  → 命中 preset_qa？ → 走预设（演示主线不变）
  → 否则：kb_search(q) 取 topK chunks
          → 拼进 system prompt 的「检索到的资料」区
          → 调模型，要求只依据资料作答、无资料时如实说没有
          → 返回 SSE 流 + sources[]（doc 标题/作者/provenance）
          → 前端「依据」区渲染真实命中项
  → 模型不可用 → 回落预设（现有逻辑保留）
```

**一个正面收益**：KB 有一条硬约束——「分步文案必须对应真实操作，**不得出现"检索知识库"等本项目没有的能力**」（2026-08-27 用户裁决）。`ChatView.tsx:74` 的注释明确写着「没有检索层，因此不写'检索知识库'」。本方案落地后**真的有了检索层**，这句可以如实写上，且「依据」从写死的档案名变成真实命中的文档——依据展示这块从"如实但空洞"升级成"如实且有据"。

>
> 1. **`store.ts` 的选择器也写死了任务集。** 它被排除在「22 个文件」之外（当时判断它只需换数据源），但 `todayCheckIns()` 直接用 seed 的模块级 `taskDefs`，等于每位患者都套林奶奶的计划。实测：新建的空档案页面显示出林奶奶的 7 项任务、「今日 0/7」，全是假的。已改为显式传入当前患者的任务。
> 2. **`CARE_ALERTS`（今日须注意）不是全局内容。** 三条各自绑定具体评估结论（洼田 Ⅱ 级、尖足步态、Braden 16 分）与对应照护动作，换患者就完全不同。已加迁移 0002 按患者存。
> 3. **工作台级页面不能读 store。** 患者列表与待处理是跨患者的，而 store 缓存只装当前患者。已改为由服务端一次算齐逐患者标记（完成数、待回复、血压超标、视频回传）。
>
> 另外 `GUIDANCE` / `PRESET_QA` / `VIDEO_STEPS` / `DAILY_REMINDERS` 一并改为从接口取 —— 否则 P1 灌进库的内容根本没被用上，P6 的审核后台改了也不生效。

`store.ts` 对外 14 个函数签名保持不变（内部换 fetch + SSE），所以 16 个消费方零改动——**这部分旧文档的判断仍然成立**。

## 8. 风险与未决红线

**必须由你或甲方解决，我做不了：**

1. **版权** —— 57 篇里仅 21 篇来源可追溯，15 篇完全无署名。分级只是如实标注，不解决授权。真实产品对外，需甲方提供原作者授权或替换语料。
2. **医疗内容专业审核** —— 21 篇（37%）带 AI 生成标注的文章会作为"脑卒中基础知识"与"政策福利"答给家属。KB 已记「转载不等于专业审核」。`videoSteps.ts` 的红线至今未解（甲方无对应内容可替换）。
3. **政策时效性叠加 AI 来源** —— 模块七 13 篇涉及医保报销、长护险、补贴，其中 **10 篇带 AI 生成标注**。政策会变、答错后果重，而来源本身就不可靠。§4.2 的 disclaimer 与降权只是兜底，**建议这一块在有权威口径替换前不对外开放**。
4. **真实患者数据授权** —— KB 边界写明「接入真实患者数据或接生产医疗系统仍未授权」。本方案只搭能力，**不代表授权已放开**。
5. **另 6 位患者的病例内容** —— KB 写明「不为演示编造第二份病例」。产品线下建议**不预置假病例**，改为提供建档功能，由真实录入产生。这条与你选的"多患者"不冲突，但需要你确认取向。

**技术风险：**

6. `sessionStorage` + Bearer 的取舍（§3.1）需你点头。
7. 22 个文件的 `PatientContext` 改造是本方案最大的一块机械工作量。
8. SSE 替代 `storage` 事件后，跨端刷新从"浏览器内存级、不可能卡"变成"要过网络"。虽然是 localhost，但这是旧文档担心的那个故障点——产品线接受它，比赛线由 tag 保护不受影响。
