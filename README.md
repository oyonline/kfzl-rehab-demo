# 居家康复智能助手

面向脑卒中居家康复场景的双端系统：**老人／家属端** 与 **康复师端**。

演示主线是一条闭环：

> 老人/家属端执行并打卡 → 康复师端远程看到 → 康复师回写指导 → 家属端收到

这条链路回答的是"区别于普通打卡小程序的价值在哪"：康复师不必上门，在工作台就能看到执行情况并给出指导。

## 两条线，先确认你在哪条上

| 线 | 位置 | 形态 |
|---|---|---|
| **比赛线** | tag `demo-competition-20260830` | 冻结的双端可交互原型，数据在浏览器内，断网可演 |
| **产品线** | `main`（本文档描述的就是这条） | 真实后端：多患者 + 多康复师 + JWT 鉴权 + SQLite 持久层 + 本地检索式知识库 + 内容审核后台 |

比赛线需要 hotfix 时从该 tag 拉分支，**不要用 main** —— main 已是另一套架构。

## 运行

```bash
pnpm install
```

开发需要**同时起两个进程**：Vite 提供前端，Express 提供 `/api`。

```bash
PORT=5099 pnpm server
```

```bash
pnpm dev
```

> ⚠️ **`PORT=5099` 不能省。** Vite 的 `/api` 代理默认打到 `127.0.0.1:5099`（`vite.config.ts`），
> 而 `server/index.ts` 的 `PORT` 默认值是 `5000`。两个默认值对不上，直接 `pnpm server` 会让所有接口请求连不上。
> 选 5099 而非 5000 是因为 macOS 的 AirPlay 接收器占着 5000。

首次启动时数据库会自动建表、跑迁移、灌种子数据 —— 不需要手动执行 `pnpm seed`。
只有 `users` 表为空（全新库）才会灌，已有数据的库不会被重灌。

部署走 `scripts/build.sh`（Vite 构建）+ `scripts/run.sh`（起 Express 并托管构建产物），
单进程、单端口，前后端同源。

比赛现场的完整安装与自检步骤见 **[docs/现场部署.md](docs/现场部署.md)**。

## 架构

### 前端

React 19 + Vite 8 + TypeScript 6，react-router-dom 7（CSR）。
样式为自建设计令牌 + 组件样式，**无 UI 组件库、无 Tailwind**。
19 个页面 + 14 个组件，双端共用一套数据契约（`src/data/types.ts`）。

### 后端

Express 5 + better-sqlite3，**49 个路由处理器**，按域拆分：

```
server/index.ts        应用入口、AI 开关、启动即建连跑迁移、空库自动灌种
server/auth/           scrypt 密码哈希、jose 签发 JWT、requireAuth 中间件
server/db/             连接与迁移执行器
server/db/migrations/  3 支迁移，28 张表 / 21 个索引
server/routes/         auth · patients · kb · content · review
server/kb/             语料导入、切片、分词、FTS5 检索
server/events/         跨端实时推送
server/seed/           种子数据
```

### 鉴权与权限

密码在服务端以 **scrypt** 哈希比对，登录成功签发 **JWT**（jose）。
令牌存 `sessionStorage`，经 `Authorization: Bearer` 头回传。
真正的安全边界在服务端每个接口的 `requireAuth` / `requirePatientAccess` 上 ——
前端改本地登录态拿不到任何数据。患者级访问控制走 `patient_members` 表，行级。

### 数据层与实时

`src/store/store.ts` 是前端唯一的数据边界。P3 把数据源从 localStorage 换成后端数据库时，
**对外的 14 个函数签名一个都没改，16 个消费方零改动**。

两个设计要点：

- **写操作仍是同步函数**，内部走"乐观更新 + 后台提交"：先改本地缓存立刻重渲染，再发请求。
  打卡还是点一下就变。提交失败时从服务端重新拉取，界面退回真实状态（对勾自己消失），
  而不是留着一个假的成功。
- **跨端实时不用 `EventSource`，用 `fetch` 流式读**。`EventSource` 不能带自定义请求头，
  而令牌走 `Authorization: Bearer`；唯一变通是把令牌塞进 URL 查询串 —— 那会让凭证进入
  浏览器历史与服务端访问日志，不可接受。

### 知识库

语料入库后切片、分词，走 SQLite **FTS5** 全文检索，答案带出处。
语料分级，检索按级别加权。导入用 `pnpm kb:import`。

> **已知限制**：语料导入源目录不在仓内，部署管线也不调用 `kb:import`，
> 因此**线上环境 `kb_documents` 为空表，检索目前只在本地成立**。详见「已知限制」。

### AI 对话

`server/index.ts` 里一个开关决定一个仓的两种跑法：容器内存在 `COZE_WORKLOAD_IDENTITY_API_KEY`
时启用真实模型，本地没有则自动关闭，`/api/chat` **立刻**返回 503，前端回落预设答案。

关键在"立刻"：本地绝不能真去调模型再等超时 —— 现场网络不可控，家属问一句话转圈半分钟，
演示就砸了。模型调用另有死超时 `LLM_TIMEOUT_MS`（默认 15s）。
需要强制覆盖用 `AI_ENABLED=1` / `AI_ENABLED=0`。

**模型白名单**（`server/index.ts` 的 `LLM_MODELS`，均经 `probe-models.ts` 实测通过）：

| 模型 | 前端标签 |
|---|---|
| `doubao-seed-2-0-lite-260215` | 标准 · 豆包 2.0 Lite（默认） |
| `doubao-seed-2-0-pro-260215` | 旗舰 · 豆包 2.0 Pro |
| `doubao-seed-2-0-mini-260215` | 极速 · 豆包 2.0 Mini |
| `glm-4-7-251222` | 备用 · GLM-4.7 |

家属端咨询页有模型选择器（`ChatView.tsx` 的 `LLM_OPTIONS`），
**与服务端白名单一一对应，改动须两侧同步**。
前端传来的 `model` 字段不被信任：不在白名单的一律回退默认值并告警。

> **平台模型快照会停运。** 原默认 `doubao-seed-1-8-251228` 被平台下线，
> 曾导致 AI 咨询整体故障（2026-08-30 发现，08-31 修复）。平台文档列出的模型
> 也可能 not found（`glm-5` / `minimax-m2.x` / `qwen-3.5` 实测均不可用），**以探测为准**。
> 演示前建议跑一遍 `pnpm tsx probe-models.ts`。
>
> 模型不可用时链路是**优雅降级**而非故障：流为空 → `ChatView` 的
> `if (!fullText.trim()) throw` 判失败 → 降级预设答案。
> 降级时「依据」仍然真实，因为知识库检索不依赖模型。

## 三条硬约束

**1. 两端必须同源部署。**
必须是同一域名下的两个路径（如 `example.com/patient` 与 `example.com/therapist`）。
前端以相对路径请求 `/api`，跨域名部署会让接口请求打空。
（产品线之前，这条的理由是"跨域名则 localStorage 不互通"；数据搬到后端后原理由已不适用，
但结论不变。）

**2. 登录态必须用 sessionStorage，不得改用 Cookie。**
Cookie 天然同源共享，一旦采用，家属端与康复师端并排开两个窗口时会互相顶掉会话，
两个角色无法同时在线，并排演示当场失效（v0.2 §5.5，实测踩过）。
sessionStorage 按标签页隔离，左右两窗可各登各的。

**3. 不引入任何外部字体、图标库或 CDN。**
图标为内联 SVG，字体用系统字体。现场网络不可控，断网也必须完整呈现。
视频素材同理必须进仓，不能用外部对象存储或 CDN 当视频源。

## 前端结构

```
src/data/types.ts      双端共用数据契约（已冻结，改动须两端同步）
src/data/seed.ts       病例、入院记录、任务计划、视频清单、打卡历史
src/data/qa.ts         咨询预设答案 ⚠️ 待专业审核
src/data/guidance.ts   饮食与健康指导 ⚠️ 待专业审核
src/data/videoSteps.ts 训练分步说明 ⚠️ 待专业审核
src/store/store.ts     数据边界：乐观更新 + 后台提交 + 流式实时
src/auth/auth.ts       登录（JWT 存 sessionStorage）
src/styles/            设计令牌与组件样式
src/components/        图标、完整档案抽屉、登录守卫
src/pages/patient/     老人 / 家属端
src/pages/therapist/   康复师端
```

家属端顶部导航四项：`/patient`（今日）、`/patient/chat`（康复咨询）、`/patient/calendar`（打卡日历）、`/patient/guidance`（饮食与健康）。

内容页统一走**列表 → 详情**：

```
/patient/videos            训练视频列表      → /patient/videos/:id
/patient/guidance          饮食与健康列表    → /patient/guidance/:id
```

训练视频**不占顶部导航**：从今日安排的任务卡点「示范视频」进入 `/patient/videos/:id`，或从今日安排标题旁的「全部训练视频」进入 `/patient/videos`。入口跟着任务走，符合"点开任务节点播放示范视频"的原始要求。

康复师端是**三层结构**，工作台级导航只放工作台级入口，患者内的分页放在详情页里：

```
/therapist                          在管患者列表（工作台首页）
/therapist/inbox                    待处理（跨患者的待回复咨询）
/therapist/review                   内容审核后台
/therapist/patients/:id             患者详情 · 随访概览
/therapist/patients/:id/consult     患者详情 · 咨询记录
/therapist/patients/:id/adherence   患者详情 · 依从性（月日历，与家属端同一组件）
/therapist/patients/:id/guidance    患者详情 · 指导记录
```

## 视频与上传的两个约定

**17 个训练视频在仓库里**（`public/videos/`，约 313 MB）。
部署从仓库构建，且现场演示要求断网可用 —— 排除在 git 之外会导致线上永远缺视频，
放外部对象存储则违反"断网可演"。这是权衡后的选择，代价是仓库体积。

`videos[].src` 为空时播放区显示海报并引导看下方分步图文，**不做假播放**；
文件缺失时 `VideoStage` 的 `onError` 兜底同样退回图文，不黑屏。

**上传是模拟的**（v0.2 §4.2 裁决）：只取文件名与大小这类元数据，
**不读取文件内容、不落盘、不上传任何数据**。未选择文件时用一个默认文件名，
保证现场即使没备好素材也能演示这一步。

打卡历史用固定模式生成而非随机数，保证每次演示看到的日历完全一致，可反复排练。

## 内容边界与数据来源

演示病例为「林奶奶」，**不对应任何可识别的真实个人**。数据来源分三类，仓内逐字段标注：

| 类别 | 说明 |
|---|---|
| **甲方实测数据** | 四张量表分值（MMSE 18 / 洼田Ⅱ / MMT 左4右5 / Braden 16）来自甲方《林奶奶_康复评估量表汇总》，评估日 2026-07-07，由其专业团队实测并署名。**本项目未生成任何分值。** |
| **标注 SYNTHETIC 的字段** | 甲方未提供、为叙事完整而虚构，**勿当作甲方数据引用** |
| **拒绝生成的字段** | 用药剂量甲方未给，`dose` 保持 `待专业确认`、`confirmed: false`，本项目不生成剂量 |

其余边界：

- 不得出现"已由医生确认""已真实接入""已同步医院系统"等冒充生产事实的措辞；
- 真实病历原件与直接身份信息不得进入本仓；
- `SUPPORT_PHONE` 当前为占位号 `400-000-0000`，**上台前必须换成机构真实服务电话** ——
  页面上出现可拨打的号码，写一个不存在的号有被真拨打的风险。

### ⚠️ 医疗内容未经专业审核

以下三个文件是本项目起草的医疗性内容，**未经康复专业人员审核不得用于正式演示**：

| 文件 | 内容 | 状态 |
|---|---|---|
| `src/data/qa.ts` | 咨询预设答案（呛咳、训练做不动、血压偏高）与自由提问兜底 | REVIEW REQUIRED |
| `src/data/guidance.ts` | 饮食与健康指导 | REVIEW REQUIRED |
| `src/data/videoSteps.ts` | 训练分步动作说明 | REVIEW REQUIRED |

起草时遵循的保守原则：不给具体剂量、不改变食物性状比例、不调整训练强度，
一律引导"记录 + 观察 + 联系康复师"，每条都带明确的升级条件。

**审核走页面，不再改代码。** 康复师端 → 顶栏「内容审核」（`/therapist/review`），
四类内容分页签逐条通过或驳回：知识库语料、咨询预设答案、饮食与健康指导、训练分步说明。
**驳回的内容立即停止对家属展示**（语料退出检索、文案不再下发）。

> 前三类由种子灌入，条数随种子变动；知识库语料**不由种子管理**，归 `pnpm kb:import`，
> 条数取决于导入了哪些语料。页面上的实际条数以运行时为准，此处不写死数字。
每次批准与驳回都写审计日志，含操作人与时间，可在同页「查看审核记录」翻阅。

上面三个文件仍是内容的**初始来源**（由种子灌进库），但审核状态只存在数据库里；
改文件头部的 REVIEW 标记不再是审核动作。

## 为什么这样设计

代码能说明"做成了什么"，说明不了"为什么不是另一种做法"。
本仓有若干看起来反常的实现 —— 不用 `EventSource`、把 313 MB 视频放进 git、
写操作保持同步签名 —— 每一条都是权衡的结果。

**[docs/adr/](docs/adr/) 记录了 16 条关键决策**，每条含背景、备选方案、裁决与后果。
被推翻的决策不删除，标注并指向新决策。

动手改这些地方之前，先读对应的 ADR，否则很可能把权衡当成疏忽"顺手修好"，
然后踩回同一个坑。

## 开发约定

- 包管理器只用 pnpm
- `src/data/types.ts` 是冻结契约，改动须两端同步
- 写运行时目录的 `.gitignore` 条目**必须带前导斜杠**（`/data/` 而非 `data/`）——
  写成 `data/` 会连 `src/data/` 一起吞掉，导致源码静默漏推、线上构建失败（2026-08-30 实测踩过）
- 交付前应对**推上去的那棵树**另做一次干净克隆构建：本地全绿照不出漏推
